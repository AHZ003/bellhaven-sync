# Writeup

**Matching approach.** I match on address first, because names change every time a facility is sold and addresses don't. A CRM account is the same facility as a website location if it's in the same state and the normalised street matches (Ave/Avenue, NW/Northwest, Pk/Pike), plus city or zip. If the CRM only has a PO Box, I require the same name plus a matching phone or administrator contact. A different real street address is always a different facility, which keeps out look-alikes like Union Square Senior Living and the Amberly Manor in Colorado. When several accounts are the same facility, I score them (already under Bellhaven, name, phone, administrator contact, billing history). A clear winner survives and the rest become duplicates. A tie is flagged for a person, not guessed, which is what happened with the three Kettering records.

The SOP check runs when a proposal is built and again at approval against live numbers. Tiffin and Marietta had revenue and outstanding AR, so they got new accounts with chow_current_account set on the old ones. Lima, Zanesville and Findlay were re-parented directly. Sandusky was sold to Millstone, whose account already existed, so I linked to it instead of creating a duplicate. Coldwater and Alliance left the website with no sign of a new owner, so they're Needs Review, not Inactive.

Re-runs are safe because proposals are built from current state (a landed fix stops showing up) and every proposal has a fingerprint in SQLite, so anything approved or rejected is never queued again.

**How I used AI.** Claude, as an agent, did almost all of the build: exploring the site and API, the scraper, matcher, review app and tests. I directed it and decided how far to trust it. I approved one proposal and rejected one myself on the demo, then had Claude review the other 24 against the live site and CRM and make each call with a reason, and verify every account afterwards (23 changed as expected, 6 created, 98 untouched, re-run proposes nothing). I used Claude Code locally to run and check things. The pipeline itself makes no LLM calls; matching is deterministic rules so the same input gives the same proposal and I can explain any decision.

**What I'd build next.** Move contacts off duplicate records and flag missing administrators; a daily digest with bulk approve for high-confidence groups; more operators (the parent and care-type map are already config); a shared database and hosted schedule instead of SQLite and cron; and use rejection reasons to tune the rules.
